## 2024-07-08 - Prevent per-second statistics recalculation
**Learning:** SwiftUI anti-pattern found: doing O(N log N) array filtering and sorting inside computed properties of a view (`StatisticsView.swift`) that observes an `AppModel` triggering updates every second (on timer tick). Swift `Array` equality checking is `O(1)` when unmodified due to buffer identity, making it extremely efficient to use as a dependency in `.onChange`.
**Action:** Cache expensive derived data calculations using `@State` variables and `.onChange(of: filterParams)` rather than computing them directly inside properties that will be evaluated on every single View render.
## 2024-07-28 - Avoid Calendar methods in tight loops
**Learning:** Performance Anti-Pattern (Swift): Using `Calendar` methods (like `.component(_:from:)` or `.isDate(_, inSameDayAs:)`) inside tight loops (like filtering a large array of `SessionRecord`s in `StatisticsCalculator`) causes severe performance bottlenecks due to ICU date math overhead. Pre-calculating a `DateInterval` outside the loop turns the check from O(N * ICU_overhead) into an O(1) bounds comparison `interval.contains(date)` for each item. Never hardcode durations (e.g. 86400 for a day) when doing this, as that breaks around Daylight Saving Time. Always use `calendar.dateInterval(of: .day, for: date)`.
**Action:** When filtering or bucketing dates in collections, always pre-calculate `DateInterval`s first to leverage Swift's highly optimized `contains` bounds checking rather than querying `Calendar` per element.
